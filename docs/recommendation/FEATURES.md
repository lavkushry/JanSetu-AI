# Behavioral feature shadow parity

The API can compare the revision-aware Redis observation projection with its consented PostgreSQL ledger after a recommended-feed transaction commits. This closes the first data-adapter parity gate for stage 3. Ranking, interest retrieval, Less/Skip suppression, permissions, exposures and pagination still use PostgreSQL. The comparison neither trains nor serves a learned model.

## Run and inspect

`make recommendation-feature-proof` creates a disposable pinned Redis 8.2.3 container on a randomly assigned loopback port, runs the real application and projection adapters against isolated PostgreSQL databases with the race detector, and removes its container on exit. It requires Docker and the existing local PostgreSQL service. It does not rebuild public services or migrate the pilot database. The existing `make recommendation-stream-proof` separately exercises Kafka delivery, consumer restart and snapshot caching.

To opt into shadow comparisons on an explicitly migrated development database, run the stream publisher/projector and set `JANSETU_RECOMMENDATION_FEATURE_SHADOW_REDIS_URL` to that projection's Redis URL before starting the API. An empty value disables the reader and comparison entirely. The API uses the worker's default `jansetu:rec:v1` namespace, with a separate client from snapshot caching. Custom projector namespaces are reserved for isolated tests and do not supply API shadow coverage.

Each comparison emits aggregate `expected`, `actual`, `matched`, `missing`, `extra`, `different` and elapsed-time counts, plus a status. It logs no viewer/stream subject, event/post identity, interests, text, location, observation values or Redis errors. `compared` means a valid projection was compared; zero mismatches are needed to establish parity for that sample. `projection_unavailable` means the dependency or its generation/schema fence could not be read safely. `generation_changed` discards all counts after an in-flight reset, withdrawal or deactivation. Ledger/authority failures are separate unavailable statuses; ineligible, anonymous and nonconsenting samples are skipped.

## Observation contract

The additional Redis hashes share the existing viewer's cluster hash tag. `observations` contains one latest observation per `(action, public post, published revision)`. `observation-seen` deduplicates its events independently of the legacy scalar projection. Metadata in `state` records `observationGeneration` and `observationSchema=1`. The reader requires both the legacy and observation generations to equal the requested generation and `enabled=true`, atomically with field reads. Decimal generation strings preserve bigint precision.

Only READ, SKIP, MORE, LESS, SATISFIED and DISSATISFIED are supported. Each observation contains event/post UUIDs, revision, action, occurrence time, normalized reading evidence and an ordering key. The ordering key compares exact UTC timestamps, then UUIDs, matching the PostgreSQL latest-event query. Older events and timestamp ties cannot overwrite a newer observation. The strict bounded decoder rejects unknown fields, malformed identities, unsupported actions and invalid reading evidence. No exposure, model, identity, media, report or OCR payload is stored in these hashes.

The projection consults live PostgreSQL authority for every personal record, clears observations and their dedup hash on generation changes or disablement, and retains the existing scalar keys for compatibility. A record previously deduplicated by a scalar-only writer can populate the new observations on replay. Legacy metadata without the new schema fence is unavailable to the new reader; it is never assumed to provide coverage. Mixed writer versions and incomplete replay can produce missing samples. Upgrade all projectors before evaluating coverage.

## Authorization and retention

The API samples at most 200 remaining frozen social references, including those subsequently suppressed by explicit negative feedback. It opens an authenticated RLS transaction, checks an active viewer's current enabled generation, obtains its private stream-subject mapping, and batch-rechecks publication, approved revision, active author/community, blocks and mutes. Only matching eligible revisions enter the ledger query and Redis read. A different session cannot sample another viewer's ledger.

The ledger selects the latest action for each eligible post revision in the current generation and preceding 30 days, using a PostgreSQL timestamp as the sample cutoff. After committing that read transaction, the API reads Redis and then checks current PostgreSQL consent/generation/activity again. No database transaction or aggregate lock is held while Redis runs. A changed generation discards the comparison, even if old cached observations remain. No Redis state authorizes a viewer or content.

Each observation and dedup field expires at its event's original absolute 30-day cutoff using [Redis HPEXPIREAT](https://redis.io/docs/latest/commands/hpexpireat/). Duplicate delivery and unrelated activity cannot extend the deadline. The reader also filters expired and post-cutoff timestamps. The script applies atomically under the [Redis scripting contract](https://redis.io/docs/latest/develop/programmability/eval-intro/). Redis and PostgreSQL clocks must be synchronized; clock drift can cause unavailable/missing shadow coverage, never authorize behavioral serving.

## Bounds and promotion gates

The reader issues bounded field lookups for six actions across at most 200 references; it never scans or fetches a viewer's full history. Each encoded observation is capped at 512 bytes. At most 10,000 events per generation are admitted to each dedup projection until earlier fields expire. Excess events can appear as missing parity, and are never silently interpreted as complete history. The optional Redis call has a 20 ms budget with retries disabled; the entire ledger/read/recheck workflow has a 120 ms budget. Failures leave the already committed feed unchanged. These budgets are engineering bounds, not measured production latency guarantees.

Historical ledger events are not automatically backfilled. Kafka's seven-day retention can cover less than the 30-day ledger window. An operator-controlled replay into the upgraded projector can fill retained records, but complete history requires a separately reviewed eligible backfill. Asynchronous delivery and interactions arriving during a sample can also produce transient missing/extra observations. Review converged coverage, lag, generation transitions and each mismatch category before considering serving integration.

The isolated proof covers six-action parity, changed/missing/extra values, replay through legacy dedup, original absolute retention, event ordering/ties, precision beyond the Lua integer range, revision isolation, bounded state, malformed caches, blocks/mutes/publication changes, foreign sessions, reset during read, live-authority replay after reset, withdrawal and stable feed pages during outage. It establishes fixture correctness. Aggregated interest/session features, sampled production coverage, retrieval backfill, analytics exports and sustained end-to-end load/cost measurements remain further stage-3 work. Learned feature parity and recommendation quality require their own dataset/model and real-user evaluation gates.
